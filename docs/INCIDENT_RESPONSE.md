# Технический план при инциденте

Этот документ описывает только технические действия. Решения об уведомлениях,
согласиях и других юридических шагах принимает юрист.

## Что считать инцидентом

- посторонний получил доступ к аккаунту наставника, Supabase, Vercel, GitHub или Gitea;
- в публичный доступ попали `.env`, резервная копия, PIN или данные учеников;
- приложение начало показывать данные одной группы другой группе;
- замечено необъяснимое удаление или массовое изменение данных;
- найдена уязвимость, через которую можно читать или менять закрытые данные.

## Первые 15 минут

1. Записать точное время, адрес страницы и что было замечено. Не публиковать в
   чате PIN, секреты, резервные копии и содержимое ученических работ.
2. Если доступ продолжается, временно закрыть Production через Vercel Deployment
   Protection или откатить его на последнюю заведомо безопасную сборку.
3. Не удалять журнал действий, логи Vercel/Sentry и подозрительные записи до
   сохранения фактов. Они нужны, чтобы понять масштаб.
4. Создать защищённую резервную копию текущего состояния командой
   `npm run backup` (`npm.cmd run backup` в PowerShell). Это снимок для анализа,
   а не автоматически безопасная копия для восстановления.

## Закрытие скомпрометированного доступа

Менять нужно только те секреты, которые могли быть раскрыты, но при неизвестном
масштабе безопаснее считать раскрытыми все административные секреты.

1. Сменить пароль базы Supabase и обновить `DATABASE_URL` и `DIRECT_URL` в Vercel.
2. При раскрытии ключа Storage сменить `SUPABASE_SERVICE_ROLE_KEY` и обновить Vercel.
3. Сменить `AUTH_SECRET`: это завершит действующие сессии и потребует нового входа.
   PIN учеников останутся bcrypt-хешами; после смены секрета их HMAC-отпечатки
   постепенно обновятся при следующей смене PIN наставником.
4. Отозвать раскрытые токены Vercel, GitHub, Gitea и Sentry.
5. Сменить PIN наставника и PIN затронутых учеников.
6. Никогда не отправлять новые значения в issue, коммит или обычный мессенджер.

## Определение масштаба

Проверить:

- `/admin/audit` — публикации, удаления, смены аудитории, PIN и проверки работ;
- Vercel Runtime Logs — подозрительные маршруты и время запросов;
- Sentry — ошибки и затронутые страницы;
- Supabase — активность базы и Storage;
- GitHub/Gitea — неизвестные входы, токены, коммиты и запуски CI;
- какие группы, профили и временные интервалы действительно затронуты.

Журнал приложения не содержит PIN, ответов, кода и текста работ. Он фиксирует
только административные изменения и не заменяет инфраструктурные логи.

## Восстановление

1. Исправить причину или выбрать последний безопасный коммит.
2. Запустить `npm run check-env`, `npm run lint`, `npm test`, `npx tsc --noEmit`
   и `npm run build`.
3. Если повреждена база, сначала выполнить сухую проверку восстановления, затем
   восстанавливать только подтверждённую копию по `docs/OPERATIONS.md`.
4. Развернуть исправление, проверить `/api/health`, вход наставника и тестового
   ученика, назначенный курс и границы доступа между группами.
5. Открывать Production снова только после этих проверок.

## Передача юристу

Передать без лишних персональных данных:

- когда инцидент начался и когда был остановлен;
- какие системы и категории данных затронуты;
- приблизительное число затронутых профилей;
- какие технические меры уже приняты;
- сохранился ли риск доступа.

Юрист определяет, кого, когда и в какой форме требуется уведомить.
