# Что передать сисадмину для размещения на Ubuntu

Актуализировано 09.09.2026 по текущей рабочей папке проекта. Это пакет для согласования переноса, а не готовый автономный установщик. Настройки Ubuntu, DNS и действующего Vercel deployment не проверялись. Последние изменения интерфейса находятся локально: нельзя считать, что они уже есть в удалённом репозитории или на Vercel.

## Короткий ответ

Да, приложение можно разместить на Ubuntu рядом с сайтом техникума. Это Next.js-приложение с серверной логикой, а не набор HTML-файлов и не PHP-сайт. Нужен постоянно работающий Node.js, обратный прокси с HTTPS и доступ к PostgreSQL. Для полного отказа от Supabase также нужны перенос изображений и доработка загрузки файлов.

| Сейчас | Роль | После полного переноса |
|---|---|---|
| Vercel | Собирает приложение, исполняет страницы, API и Server Actions, отдаёт статические файлы. Вход, админка и запись прогресса исполняются здесь как код приложения | Ubuntu: Node.js под systemd + nginx/существующий веб-сервер с HTTPS |
| Supabase PostgreSQL | Пользователи, хеши PIN, уроки, доступы, прогресс, монеты, достижения и работы | Отдельная PostgreSQL-БД приложения |
| Supabase Storage | Загруженные изображения; код использует публичный бакет lesson-images | Постоянный каталог/объектное хранилище и раздача файлов |
| Auth.js / next-auth | Собственная авторизация по профилю/имени и PIN, JWT-cookie на 8 часов | Продолжает работать внутри Node.js; устанавливать Supabase Auth не нужно |
| Vercel Analytics / Speed Insights | Дополнительная аналитика посещений и скорости | Удалить/отключить при полном отказе от Vercel |

## Что отправить завтра

1. Этот файл и MIGRATION_SYSADMIN.md — описание устройства, требований, данных и порядка переноса. MIGRATION_FOR_OWNER.md — список личных проверок наставника.
2. Доступ к согласованной актуальной версии кода либо отдельный архив исходников. Включить src (без generated/prisma), public, prisma со всеми миграциями, scripts, package.json, package-lock.json, next.config.ts, prisma.config.ts, tsconfig.json, postcss.config.mjs и необходимые конфигурации проверок. Сохранить public/avatars. При передаче репозитория сначала включить последние локальные изменения в согласованную ревизию.
3. По защищённому каналу — свежую копию действующей БД, отдельно полный экспорт файлов lesson-images. Если экспорт делает администратор, вместо копий согласовать доступ к правильному облачному проекту. Не посылать общую папку с локальными и тестовыми базами вперемешку.
4. Отдельно — рабочие настройки окружения/секреты назначенному исполнителю. В общий архив и переписку пароли, service_role и AUTH_SECRET не включать. Для новой локальной БД администратор создаёт собственные реквизиты.
5. Согласованный адрес сайта и несколько примеров для сверки: ученик, его XP/монеты/прогресс, урок с картинкой, работа с комментарием, выданные пиксели. PIN всех учеников не нужен; старые входы сохраняются через User.pinHash.

Не включать в архив кода node_modules, .next, .next-e2e, .env, .vercel, .git, test-results, backups, старые проекты и тестовые fixtures. Зависимости и сборку заново создать на Linux. Не отправлять всю папку диска G целиком.

Последний найденный локальный JSON-бэкап — backup-2026-09-08T21-21-58-217Z.json. Он сделан до миграции учёта пикселей и не заменяет финальную свежую копию. На момент этого обследования новый экспорт БД и Storage не выполнялся.

## Что нужно от администратора

- Отдельный поддомен, например quantorium.<домен-техникума>; конкретный адрес определяет администратор. Размещение в подпапке потребует отдельной настройки ссылок/basePath.
- Отдельный пользователь службы и Node.js 24 LTS с актуальным патчем; версия предлагается для нового сервера, запуск именно этого приложения на Ubuntu ещё не проверен. Next.js 16.2.9, React 19.2.4, Prisma 7.8.0; зависимости фиксирует lock-файл.
- Отдельная PostgreSQL-БД. Версию исходного Supabase узнать перед выбором целевой версии и дампа; не делать неподтверждённый downgrade.
- Для начального обсуждения: примерно 2 vCPU / 4 ГБ RAM / 20 ГБ SSD плюс данные и резервные копии. Это предварительный бюджет, не измеренная потребность; сборке может понадобиться больше памяти. Учесть уже работающий сайт техникума.
- HTTPS, обратный прокси на внутренний порт Node.js, например 3100; снаружи не открывать Node.js и PostgreSQL. Служба systemd с автозапуском и перезапуском, журналы, ежедневные копии БД и файлов, копия вне этого сервера.
- Ответ: сайт только в локальной сети или доступен ученикам из дома; кто управляет DNS/сертификатом; кто отвечает за обновления и восстановление.
- Доступ к npm и Google Fonts на этапе сборки. Браузеры сейчас загружают Python/Pyodide с jsDelivr; Scratch и YouTube также внешние. Размещение на своём сервере само по себе не делает эти материалы доступными без интернета.

## Два варианта запуска

**Сначала убрать только Vercel.** Развернуть текущий код на Ubuntu, сохранив PostgreSQL и Storage в Supabase. Это самый короткий путь к проверке хостинга: переписывать авторизацию не требуется. Настроить домен, AUTH_URL/AUTH_TRUST_HOST, службу, HTTPS и убрать Vercel-аналитику при отказе от неё. Если пробный экземпляр подключён к рабочей БД, его действия меняют реальные данные; проверку безопаснее проводить на изолированной копии. Такой этап не является уходом от Supabase.

**Полностью убрать оба облака.** Помимо размещения Node.js, перенести PostgreSQL и изображения. До отключения Supabase разработчику необходимо:

- заменить src/app/api/admin/upload-image/route.ts на постоянное локальное хранилище, сохранив авторизацию наставника, ограничения размера/типов, уникальные имена и ответ { url };
- заменить проверку SUPABASE_URL/SUPABASE_SERVICE_ROLE_KEY в scripts/check-env.mjs и связанные проверки окружения;
- скопировать файлы и заменить подтверждённые старые Storage URL в контенте и истории работ, сохранив JSON/Markdown;
- заменить metadataBase в src/app/layout.tsx на новый адрес, отключить @vercel/analytics и @vercel/speed-insights, проверить CSP при новом адресе изображений;
- согласовать сохранение Sentry и внешних учебных материалов.

Эти доработки локального хранилища пока НЕ выполнены. Просто удалить ключи Supabase нельзя: загрузка картинок перестанет работать, проверка окружения завершится ошибкой. Dockerfile, Compose и systemd-unit в текущем проекте не подготовлены; Docker не обязателен для запуска.

## Технические ориентиры и сохранность данных

Окружение приложения: DATABASE_URL, DIRECT_URL, AUTH_SECRET, AUTH_URL=https://<согласованный-домен>, AUTH_TRUST_HOST=true; NODE_ENV=production для работающей службы. Прокси должен фильтровать Host и корректно задавать forwarded-заголовки. Для обычного production не копировать DATABASE_SCHEMA=e2e, KVANTOLINGO_E2E=1 и staging-переменные из тестовых запусков. Пока используется облачное Storage, нужны и SUPABASE_URL/SUPABASE_SERVICE_ROLE_KEY. Секрет можно перевыпустить: это потребует повторного входа, но не изменит PIN.

Обычная последовательность после подготовки кода и окружения: npm ci --include=dev → npx prisma generate → согласованное восстановление новой БД и проверка её миграционной истории → npx prisma migrate deploy → npm run check-env → npm run build → npm run start -- --hostname 127.0.0.1 --port 3100 под systemd. Если БД временно остаётся в облаке, восстановление не требуется. Миграции на исходной рабочей БД во время репетиции не запускать. Для полной локальной версии check-env сначала должен быть доработан.

Не запускать npm run dev в production. Не выполнять seed, migrate reset или db push для переноса существующих данных. Не восстанавливать в БД основного сайта техникума. При выборе JSON-восстановления сначала создать схему миграциями; при нативном дампе сохранить и согласовать _prisma_migrations, не создавать конфликтующую схему поверх дампа. Точные варианты описаны в MIGRATION_SYSADMIN.md.

В текущей Prisma-схеме 23 прикладные таблицы плюс служебная история _prisma_migrations. Обязательно сохранить User.avatarId, User.pixelsRedeemed и PixelRedemption (дата/наставник/монеты/пиксели): иначе потеряется учёт ручной выдачи и лимита 60 пикселей за курс.

Сначала выполнить пробное восстановление. В день переключения закрыть запись на старом сайте, снять финальные согласованные копии БД и файлов, восстановить и сверить. Проверить вход ученика и наставника, админку, старые картинки и загрузку новых, сохранение урока, балансы, достижения, историю пикселей, работы и /api/health. Старый сайт сохранить для отката, но не оставлять две независимо записывающие версии. Облака отключать после приёмки и согласованного периода наблюдения.
