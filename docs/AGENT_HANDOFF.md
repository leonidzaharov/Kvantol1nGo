## 2. Решения владельца

1. Scratch предназначен для вводного направления, Python для углублённого.
   Не проектировать обязательный переход Scratch -> Python.
2. Новые тренажёры должны быть полезны обоим направлениям. Базовый сценарий:
   попытка, правильный ответ и объяснение, другой вопрос, повторение навыка.
3. Не строить новые возможности вокруг функции «Начать урок». Владелец
   ей не пользуется; её оптимизация и удаление не выполнялись.
4. Короткая проверка может давать 5 монет, полноценная практика 20.
   Сейчас это ручные пресеты наставника, а не автоматическая классификация.
5. Готовые уроки, MD, JSON вопросов и иллюстрации хранить вне репозитория
   приложения, по умолчанию в отдельных папках внутри `E:/Работа/Материалы`.
   В платформу добавлять через админку.
6. Для локальной проверки нужен один наставник. Копировать настоящих учеников
   и рабочую базу не требуется.
7. Обычный запуск владельца: `npm run dev` из Git Bash.
8. Не использовать длинное тире в новом тексте и сообщениях коммитов.
   Использовать обычный дефис. Не добавлять трейлеры авторства генератора.
9. Коммит и push делать по запросу. Последний такой запрос выполнен;
   создание этого документа не является разрешением на следующий push.

## 3. Что внедрено в учебном интерфейсе

Добавлен явно обозначенный формат `practice-v1`. Старые уроки продолжают
использовать классический `QuestRunner`. Новая практика подключена к
странице урока, предпросмотру наставника, редактору, сохранению и импорту.

Последовательность:

1. Короткая теория, разделённая на шаги, если она задана.
2. Самостоятельный ответ ученика и явная кнопка проверки.
3. Правильный ответ и объяснение после верной или неверной попытки.
4. Неверно решённый пункт возвращается с другим вариантом после двух
   других вопросов. При короткой очереди повторение наступает раньше.
5. Просмотр объяснения сам по себе не закрывает пункт.
6. После решения обязательной части ученик отдельно подтверждает финиш.
7. Дополнительные задания доступны после основного финиша и необязательны.

Для одного навыка нужны 2-3 содержательно разных равноценных варианта.
Новый формат поддерживает `choice`, `text`, `match`, `code`. Программирование
с исполнением Python/JavaScript также сохраняется в классическом формате.
Короткий текст проверяется существующим сравнением с эталоном. Оценивание
развёрнутого рассуждения или проверка через ИИ не добавлялись.

## 5. Формат и совместимость MD/JSON

Источник точного контракта: [PRACTICE_FORMAT.md](PRACTICE_FORMAT.md).

- Классический `Lesson.content` остаётся JSON со строкой `theory`, массивами
  `questions` и `bonusQuestions`, без обязательного поля `format`.
- Новая практика содержит `format: "practice-v1"`, теорию и два массива
  пунктов. У пункта есть `id`, необязательная `intro` и `variants`.
- Неизвестный формат и повреждённый документ отклоняются. Они не должны
  превращаться в пустой завершённый урок.
- Основных пунктов 1-50, бонусных до 20, вариантов на пункт 2-3.
  Максимальный размер нового документа 256 KiB UTF-8.
- ID ограничен 48 символами. ID пунктов уникальны во всём уроке,
  ID вариантов внутри пункта. В `match` ID карточек уникальны в обеих колонках.
- В `match` по 2-8 карточек в каждой колонке. Полное решение связывает
  каждую карточку ровно один раз.
- `explanation` обязателен у каждого варианта. Неизвестные поля нового
  формата отклоняются, чтобы опечатка не уничтожила данные при сохранении.
- Существующие классические `choice`, `text`, `code` и старые допустимые
  формы вопросов сохраняются. Не выполнять массовую конвертацию старых уроков.

Обычный MD меняет теорию и сохраняет текущие вопросы. MD с относительными
изображениями импортируется через «Импорт из папки». Прямой импорт одного
MD предлагает выбрать папку, если нужны соседние картинки.

Для единого файла теории и вопросов поддерживается ровно один fenced-блок
с языком `kvantolingo`. Внутри находится JSON импорта. Подробный пример
есть в документе формата. Эта команда:

- извлекается до отображения Markdown и загрузки изображений;
- не попадает в ученическую теорию вместе с решениями;
- предлагает добавить задания, заменить их или отменить импорт;
- при неправильном JSON, неизвестной версии, повторном или незакрытом блоке
  выдаёт ошибку до замены формы;
- внутри более длинного обычного ограждения остаётся примером текста.

`parseLessonMarkdown` возвращает `{ theory, questionImport }`.
`parseLessonDocument` возвращает classic, practice-v1 или `null`.
`importTheoryFolder` сохранил прежние поля результата и добавляет
`questionImport` только при наличии команды.

## 6. Прогресс, права и монеты

Новых таблиц, колонок и миграций для практики не добавляли. Используются
существующие `Lesson.content` и `UserLessonProgress`.

- В начальных данных ученика нет `correctIndex`, `correctAnswer`,
  `correctPairs`, `referenceSolution`, `expectedOutput` и `explanation`.
  Публичные поля перечисляются явно.
- После валидной попытки action возвращает `checked` с разбором.
  Неполная/повторная/подменённая структура пар получает `invalid` без эталона.
- Проверяются сессия, доступ к уроку, ID пункта/варианта, секция и revision.
- Для предпросмотра используется отдельный action с проверкой наставника.
  Он не записывает ученический прогресс и не начисляет монеты.
- `answeredCore` хранит точные индексы подтверждённых основных решений.
  В практике `answeredCount` не означает решённый префикс.
- Завершение новой практики проверяет все обязательные индексы.
  Прежний fallback по счётчику оставлен только классическим урокам.
- Выплата остаётся в `completeLesson`; повторный запрос или повторное
  прохождение не создаёт вторую основную награду. Бонусы не дают отдельную выплату.
- Проверка редакции и запись ответа согласованы с сохранением через
  транзакционные advisory locks PostgreSQL. Удаление урока тоже учитывает блокировку.
- Содержимое опубликованной практики и практики с прогрессом менять нельзя.
  Для новых вопросов создают отдельный урок. Метаданные можно редактировать.
- Сетевой сбой проверки сохраняет ввод. Сбой финиша позволяет повторить
  подтверждение без повторного решения обязательной части.
- `AbortSignal` используется только локально. Он не сериализуется в Server Action
  и не отменяет уже выполненную запись в базе.

Прежняя авторизация не переписывалась. В рабочей базе бывают `User.id`
не в формате UUID: использовать `UserIdSchema` из `server-guard.ts`.

## 7. Сопоставление и нагрузка

«Протяни верёвочку» реализовано через две колонки карточек и SVG-линии.
Поддерживаются мышь, касание и клавиатура. Карточки перемешиваются независимо
со стабильным seed, чтобы не ломать гидратацию.

Положение временной линии обновляется через ref/requestAnimationFrame.
ResizeObserver пересчитывает координаты; наблюдатель и кадры очищаются.
Движение указателя не создаёт запросов к серверу и не должно перерисовывать
весь урок через React state. Pyodide для сопоставления не загружается.

Новый runner не добавляет polling, heartbeat и WebSocket. Проверка ответа
может записывать существующую сессионную телеметрию. Сбой этой телеметрии
не должен превращать успешно проверенный ответ в ошибку.

Полноценный замер памяти и конкурентной работы класса из 30 учеников
не проводился. Не представлять ограничения размера JSON как измерение
реального потребления памяти сервером. Нагрузочную проверку проводить
отдельно на предназначенном тестовом окружении.

## 8. Причина прежнего зависания localhost

Старый `.env` всё ещё подключал разработку к Supabase. В журнале были
`Connection terminated unexpectedly` и переход в админку длительностью
около 92 секунд. Индикатор Next.js Rendering сопровождал незавершённую
навигацию; бесконечный цикл React подтверждён не был.

Диагностика показала быстрое чтение маленьких ответов и зависание
синтетического ответа около 100 КБ через старое подключение.
Список админки забирал содержимое 16 уроков, около 92 КБ.
Точный механизм сетевого сбоя старого облака отдельно не установлен.

Временно добавленные ограничения ожидания и повтор безопасных чтений
не устранили причину и затем полностью удалены вместе с
`db-development.ts` и его тестами. `src/lib/db.ts` вернулся к обычному
Prisma-клиенту. Не восстанавливать эти обходы для нового локального окружения.

  противоречащий `.env.local`: служебные команды проекта используют dotenv.
- PostgreSQL работает отдельным фоновым процессом, служба Windows не создавалась.

- В конце проверки сайт и локальная PostgreSQL были остановлены;

## 11. Рабочий сервер и публикация

Рабочая версия находится на Debian в техникуме, а не в локальной базе.
Факты конфигурации взяты из `AGENTS.md` и файлов проекта, не из нового
обследования сервера:

- Локальный адрес сервера: `192.168.0.28`, внешний сайт:
  `https://it-quan.kpcollege.ru`.
- SSH-пользователь `leonid`. Прямой SSH с разработческой машины ранее
  был недоступен; команды на сервере выполняет владелец/администратор.
- Next слушает `192.168.0.28:3100`. Не заменять адрес на loopback в службе.
- Серверный env: `/etc/quantorium.env`.
- Постоянные картинки: `/var/lib/quantorium/uploads`.
- Бэкапы: `/var/backups/quantorium`.
- Репозиторий: `/opt/quantorium/repository`, ветка `production`.
- Релизы: `/opt/quantorium/releases`, активный путь: `/opt/quantorium/current`.
- Порядок: push в `main`, GitHub CI, продвижение `production`, затем
  серверный таймер при условии, что он включён.

Изменений схемы Prisma, новых миграций, `auth.ts`, `server-guard.ts`,
служб Debian и скрипта автодеплоя для этой работы не делали.
Серверные actions уроков и прогресса расширены ради практики; утверждать,
что весь backend оставлен без изменений, было бы неверно.
Для будущих задач серверные файлы остаются защищёнными правилами `AGENTS.md`.

Рабочие env, PostgreSQL и uploads через серверные команды не изменялись.
Не копировать локальную `.env` и переносимую Windows-базу на Debian.
После обновления открытая вкладка админки может потребовать Ctrl+F5
из-за несовпадения сборок Server Actions.

## 14. Как продолжать

1. Прочитать `AGENTS.md`, проверить `git status` и текущую ветку.
2. Для просмотра запустить `npm run dev`, войти наставником через `/mentor`.
   Учётные данные читать локально, не переносить их в документы или чат.
3. Для нового тренажёра сначала сверить формат с кодом и
   [PRACTICE_FORMAT.md](PRACTICE_FORMAT.md), затем менять редактор, страницы,
   проверку и тесты согласованно.
4. Перед изменением Next.js API читать соответствующий раздел
   `node_modules/next/dist/docs/`. Не обновлять Next/Prisma попутно.
5. Перед сборкой остановить dev-сервер, чтобы не конфликтовал `.next`.
6. Запускать проверки соразмерно изменениям. Интеграционные и E2E-тесты
   используют только локальное/специально выделенное тестовое подключение.
7. Перед коммитом проверить список файлов и секреты. Перед push помнить,
   что `main` связан с продвижением `production` после CI.
8. Не запускать `migrate reset`, разрушительный seed или восстановление
   поверх рабочей базы. Работы с сервером требуют отдельной задачи.
