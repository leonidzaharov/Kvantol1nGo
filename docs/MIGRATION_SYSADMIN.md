Это техническое задание и порядок подготовки переноса, а не отчёт о выполненной миграции. Изучены исходники, миграции, конфигурация, скрипты эксплуатации и локальная документация Next.js. ## 1. Что сейчас работает

Это самостоятельная учебная платформа: группы и ученики, курсы и уроки, задания, прогресс, XP, уровни, монеты, достижения, материалы, очные занятия с живой панелью наставника, ручные работы с версиями ответов и проверкой, журнал административных действий.

| Компонент | Реализация в проекте | Что потребуется на сервере |
|---|---|---|
| Приложение | Next.js 16.2.9, React 19.2.4, TypeScript, App Router, Server Actions и API | Постоянно работающий Node.js-процесс; статический HTML-хостинг не подходит |
| Размещение | `vercel.json`: Next.js, регион `fra1`, `npm run vercel-build` | Собственный запуск, TLS, обратный прокси, логи и перезапуск |
| База | PostgreSQL через Prisma 7.x, `@prisma/adapter-pg`, `pg` | Отдельная БД PostgreSQL и отдельные учётные данные |
| Авторизация | Auth.js / next-auth 5 beta, Credentials, bcrypt, JWT | Сохранить таблицу User и настроить AUTH-переменные |
| Изображения редактора | Supabase Storage, публичный бакет `lesson-images` | Экспорт файлов и замена обработчика загрузки |
| Наблюдение | Sentry по DSN; Vercel Analytics и Speed Insights подключены в layout | Решить, какие сервисы оставить; настроить собственный мониторинг |

Точные версии зависимостей фиксирует `package-lock.json`; использовать `npm ci`. Prisma генерирует клиент в `src/generated/prisma`, каталог исключён из Git и создаётся заново.

Supabase Auth, Realtime и Edge Functions в действующем коде приложения не обнаружены. Установка всей платформы Supabase на сервер для существующей авторизации не требуется. Проверить вручную, нет ли дополнительных объектов/настроек только в облачной БД: исходники не доказывают их отсутствие.

## 2. Авторизация и права — что обязательно сохранить

- Ученик выбирает направление, группу, профиль и вводит PIN. Для новых учеников предусмотрен PIN из 4 цифр.
- Наставник входит на `/mentor` по имени и PIN; инструменты создания требуют 8–10 цифр. Этот способ входа допускает только `isAdmin=true`.
- `User.id` — постоянный идентификатор; `pinHash` — bcrypt-хеш. Перенести их без пересоздания пользователей. Перенести также `isAdmin`, `groupId`, публичный ник, приватную подпись наставника и остальные поля.
- При сохранении хешей старые PIN продолжат работать. Открытые PIN из хешей не восстанавливаются; для миграции список PIN учеников не нужен. Для проверки нужен известный действующий PIN тестируемого профиля.
- Сессия — JWT в cookie, срок до 8 часов. Таблиц аккаунтов OAuth или серверных сессий в Prisma-схеме нет. При новом домене пользователи войдут заново. Замена `AUTH_SECRET` тоже завершит старые сессии, но не изменит PIN и данные.
- Пять неудачных попыток за пять минут блокируют дальнейшие попытки профиля до выхода из окна. Источник — `src/auth.ts`; старый комментарий про 15 минут в скрипте очистки не соответствует действующей логике.
- Права наставника проверяются по БД на сервере (`src/lib/server-guard.ts`), доступ к курсам/материалам — по публикации и назначениям группам. Настройки доступа должны мигрировать вместе с контентом.
- Интеграции с учётными записями сайта техникума, AD/LDAP, SSO и почтового восстановления в текущей авторизации нет. Их добавление — отдельная задача.

## 3. Размещение рядом с существующим сайтом

Предлагаемая схема: отдельный поддомен → существующий nginx/Apache/IIS с HTTPS → отдельный Node.js-процесс → отдельная PostgreSQL-БД. Загруженные файлы — в постоянном каталоге вне каталога релиза, с отдельной резервной копией.

Поддомен согласовать с администратором. Размещение в `/kvantorium` потребует дополнительных изменений: сейчас маршруты и ссылки начинаются от корня, `basePath` не настроен. Не заменять конфигурацию основного сайта техникума и не использовать его БД для восстановления.

Для Linux можно использовать отдельную VM/контейнер или отдельного системного пользователя и службу systemd. Для Windows администратор выбирает эквивалент службы и проксирования. Готовых Dockerfile/Compose и конфигурации службы в обследованном корне проекта нет.

Node.js: предлагается актуальный патч 24.x LTS. Установленный Prisma допускает `^20.19 || ^22.12 || >=24.0`; CI пока настроен на Node 20 — это не основание выбирать его для нового сервера. Переход на 24 проверить сборкой и тестами. Статус ветки: [официальные загрузки Node.js 24](https://nodejs.org/en/download/archive/v24).

PostgreSQL: CI использует 16; фактическую версию Supabase нужно узнать отдельно. Целевую версию выбрать после проверки совместимости экспорта и пробного восстановления, не планировать слепой downgrade.

Для первоначального обсуждения ресурсов: отдельный бюджет около 2 vCPU, 4 ГБ RAM и 20 ГБ SSD плюс фактический объём файлов/БД и резервных копий. Это предварительная оценка, не измеренная потребность; сборка может потребовать больше памяти. До размещения проверить запас ресурсов основного сайта и нагрузку целого учебного класса.

Прокси должен:

- принимать только согласованные имена хостов, завершать TLS, передавать корректные `Host`, `X-Forwarded-Host`, `X-Forwarded-Proto` и перезаписывать недоверенные forwarded-заголовки;
- закрывать прямой внешний доступ к Node.js и PostgreSQL; пример внутреннего порта приложения — 3100, выбрать свободный;
- пропускать API и POST Server Actions, cookie, заголовки Next.js и CSP; не кэшировать персональные страницы и ответы авторизации;
- сохранять потоковую отдачу, отключить нежелательную буферизацию; лимит тела загрузки задать выше 5 МБ с учётом multipart, например 8 МБ. Приложение само ограничивает изображение 5 МБ;
- не добавлять конфликтующую CSP. В `src/proxy.ts` используется nonce, в `next.config.ts` — HSTS и другие защитные заголовки.

Один экземпляр приложения достаточен для начальной проверки. Дополнительный rate limiter загрузок живёт в памяти процесса; при нескольких экземплярах лимиты не общие. Живая панель делает HTTP-опрос раз в 3 секунды, отчёт активности ученика — раз в 10 секунд. Отдельный Supabase Realtime/WebSocket-сервис для этого не нужен.

## 4. Переменные окружения

| Переменная | Назначение и действие |
|---|---|
| `DATABASE_URL` | Рабочее подключение Prisma к новой БД; отдельный пользователь с необходимыми правами |
| `DIRECT_URL` | Подключение для миграций и большинства эксплуатационных скриптов. Без пулера можно указать тот же адрес БД; при разделении ролей выдать миграционные права только служебной роли |
| `AUTH_SECRET` | Случайный секрет минимум 32 символа. Перенести защищённо либо выпустить новый и запланировать повторный вход |
| `AUTH_URL` | Зафиксировать согласованный внешний HTTPS-адрес сайта; в локальном `.env` не обнаружен |
| `AUTH_TRUST_HOST=true` | Для доверенного обратного прокси; в локальном `.env` не обнаружен. Не заменяет фильтрацию хостов на прокси |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | Сейчас обязательны для загрузки и `check-env`. После реализации локального хранилища убрать зависимость из кода и проверки, затем удалить секреты из нового окружения |
| `NEXT_PUBLIC_SENTRY_DSN` | Опциональная отправка ошибок. При отказе от Sentry убрать до сборки, поскольку значение входит в клиентский пакет |
| `NODE_ENV=production` | Для работающего сервиса; на этапе установки нужны также devDependencies для сборки и Prisma CLI |
| `KVANTO_DEPLOYMENT_ENV=production` | Маркер окружения; не переносить staging-настройки |
| `DATABASE_SCHEMA` | Обычно не задавать: рабочая схема `public`. Это настройка рантайма, отдельно от `?schema=` в URL для Prisma CLI |
| `DB_SLOW_QUERY_MS` | Необязательный порог журналирования медленных запросов |

Не переносить в production тестовые `KVANTOLINGO_E2E`, `STAGING_*`, `SEED_FORCE`, `RESOURCE_SEED_FORCE`, `VERCEL_ENV=preview`. В `.env` локально обнаружены первые два DB-подключения, два Supabase-параметра, AUTH_SECRET и Sentry DSN. Сверить с production в Vercel; локальная конфигурация может отличаться.

Эксплуатационные скрипты читают `.env` через dotenv, Next.js также поддерживает свои env-файлы. Служба и миграции должны получать согласованные значения; нельзя допустить, чтобы приложение писало локально, а скрипт восстановления использовал старый облачный `DIRECT_URL`. Секреты хранить в защищённом env-файле/хранилище секретов вне публичного каталога и Git.

Поведение AUTH-переменных подтверждено кодом установленного пакета и [документацией Auth.js](https://authjs.dev/getting-started/deployment).

## 5. Что передать и выгрузить

### Код и конфигурация

Репозиторий согласованной production-ревизии: `src`, `public`, `prisma` со всеми миграциями, `scripts`, `package.json`, `package-lock.json`, корневые настройки и документация. Локальная ревизия выше ещё не сверена с Vercel. Передать отдельно согласованные секреты и настройки домена. Не переносить Windows `node_modules` и `.next`: собрать на целевой платформе.

`backups/` и `.env` исключены из Git. Клонирование репозитория их НЕ переносит. Старые архивы, `duo/`, `assets ux/` не являются рабочим приложением.

### База данных

В Prisma описаны 23 прикладные таблицы (отдельно сохраняется служебная _prisma_migrations):

- `User`, `Group`, `LoginAttempt`, `AdminAuditLog`;
- `Category`, `Lesson`, `CategoryGroupAssignment`, `LessonGroupAssignment`, `UserLessonProgress`;
- `ClassSession`, `SessionStudentProgress`, `SessionQuestionProgress`;
- `ReviewAssignment`, `ReviewAssignmentGroup`, `ReviewAssignmentUser`, `ReviewSubmission`, `ReviewSubmissionVersion`;
- `Achievement`, `UserAchievement`, `Resource`, `ResourceGroupAssignment`, `UserResource`, `PixelRedemption`.

Переносить все поля, связи, идентификаторы и последовательности, а не только пользователей и уроки. Схему и её историю задают Prisma migrations; для нативного дампа также учитывать `_prisma_migrations`. Контент созданный в админке находится в БД, seed-файлы не заменяют его копию.

### Изображения и остальные файлы

Выгрузить ВСЕ объекты бакета `lesson-images` с сохранением путей, типов содержимого и перечнем размеров/контрольных сумм. Для больших списков учитывать пагинацию и вложенные пути. Проверить, существуют ли другие используемые бакеты/объекты. Сохранить `public/` из кода.

Дамп БД не содержит файлов Storage — это отдельно подтверждено [документацией Supabase о бэкапах](https://supabase.com/docs/guides/platform/backups). В уроках уже сохранены абсолютные публичные URL Supabase. После копирования файлов нужно заменить ссылки на новый адрес и проверить соответствие каждого объекта. Проверить `Lesson.content` (JSON в строке), `Resource.body/url`, инструкции и версии ручных работ и другие текстовые поля на ссылки к старому хранилищу. Изменять только подтверждённые URL, с сохранением структуры JSON/Markdown и истории.

Ссылки на YouTube, Scratch и внешние статьи не содержат самих внешних материалов: перенос БД сохраняет ссылки, но не делает их локальными.

## 6. Изменения кода до полного отключения облаков

Эти изменения выявлены, но в рамках обследования не выполнялись.

1. `src/app/api/admin/upload-image/route.ts`: заменить Supabase Storage записью в постоянное локальное хранилище. Сохранить проверку наставника, уникальные имена, ограничения PNG/JPEG/GIF/WebP, 5 МБ, лимит 30 загрузок/минуту. Возвращать совместимый `{ url }`. Настроить раздачу файлов и права службы. Не хранить загрузки только внутри временного контейнера или сменяемого релиза.
2. `scripts/check-env.mjs`: убрать безусловное требование облачных SUPABASE-параметров, добавить проверку реального локального хранилища. Сейчас проверка принимает только `https://<project-ref>.supabase.co`; произвольный локальный URL не пройдёт. Пересмотреть связанные проверки в `scripts/env-safety.mjs` и тесты.
3. Мигрировать файлы и URL в БД; `src/proxy.ts`: скорректировать CSP при отдельном домене файлов. Для файлов на том же origin уже разрешён `'self'`. После проверки удалить ненужные облачные разрешения.
4. `src/app/layout.tsx`: заменить `https://quantorium.vercel.app` в metadata, убрать/отключить Vercel Analytics и Speed Insights, если цель — полный отказ от Vercel.
5. Решить судьбу Sentry. Для полностью локального сбора ошибок убрать DSN перед сборкой и организовать серверные журналы/оповещения.
6. Согласовать доступ в интернет. Pyodide загружается с jsDelivr в браузерах учеников; Scratch/YouTube встроены извне. Для автономной сети разместить Pyodide локально и изменить его базовый URL, подготовить альтернативы внешним материалам. Шрифт Nunito сейчас берётся через `next/font/google`: сборке нужен доступ к Google Fonts либо переход на локальный файл шрифта. Установке зависимостей нужен доступ к npm или внутреннему зеркалу.
7. Подготовить службу, резервирование, выпуск релиза и безопасное обновление. `vercel.json` на собственном сервере не создаёт службу, расписание или TLS автоматически. GitHub/Gitea workflows проверяют код; готового развёртывания на сервер техникума в них нет.

Временный промежуточный вариант — перенести Node.js и PostgreSQL, сохранив облачное Storage. Это позволит проверить сервер раньше, но не будет завершённой миграцией из Supabase.

## 7. Порядок переноса данных

### Подготовка и репетиция

1. Установить точную production-ревизию, версии БД, объёмы, перечень Storage и источник действующих секретов. Согласовать дату, ответственных, новый адрес и период недоступности.
2. Создать изолированную новую БД, каталог файлов, отдельный сервис и тестовый адрес. Тестировать реальные данные только в согласованной закрытой среде техникума.
3. Выбрать ОДИН путь восстановления ниже и отрепетировать его. Зафиксировать время, число строк каждой таблицы, число файлов, размеры и контрольные суммы. Проверка одного `/api/health` недостаточна.

**Вариант A — существующий JSON-инструментарий проекта.** На исходном окружении `npm run backup` читает `DIRECT_URL`, иначе `DATABASE_URL`, и пишет `backups/backup-*.json`. Берёт таблицы `public`, но не создаёт транзакционный снимок сразу всех таблиц. Поэтому финальный экспорт выполнять только после остановки всех записей: пользователей, наставников, старых deployments и фоновых скриптов. Не полагаться только на просьбу детям не заходить.

На новой пустой БД сначала применить миграции ровно переносимой ревизии. Затем штатный restore: он не создаёт схему, пропускает `_prisma_migrations`, очищает прикладные таблицы, вставляет данные в порядке внешних ключей и восстанавливает счётчики. Не запускать на БД сайта техникума или исходной production-БД. При предупреждении о пропущенных/лишних таблицах остановиться и разобраться; не считать частичный перенос успехом.

Пример последовательности для администратора в Linux shell, после настройки окружения ТОЛЬКО новой БД:

```bash
npm ci --include=dev
npx prisma generate
npx prisma migrate deploy
npm run restore -- --file /secure/migration/backup-FINAL.json
# Только после проверки плана и целевой БД; --yes очищает её данные:
npm run restore -- --file /secure/migration/backup-FINAL.json --yes
```

Использовать явный путь файла, а не автоматический выбор «последнего». На Windows команды проекта можно запускать как `npm.cmd` и `npx.cmd`. Локально найден последний по времени файл `backup-2026-08-21T09-00-46-261Z.json`, размер 261326 байт: он устарел относительно даты обследования; содержимое и восстановимость здесь не проверялись. Это не замена свежему финальному экспорту.

**Вариант B — нативный дамп PostgreSQL.** Администратор может выбрать `pg_dump` custom format для согласованного набора прикладных объектов и `pg_restore` в отдельную пустую БД без старых владельцев/ACL. Такой дамп даёт согласованный снимок. Проверить зависимости схем, расширения, роли, `_prisma_migrations` и совместимость версий инструментов; не переносить вслепую системные схемы Supabase. Не накладывать создание таблиц Prisma поверх полного schema+data restore. После восстановления сверить историю миграций и применить только действительно недостающие. Порядок и ограничения версий: [PostgreSQL pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html).

Для обоих вариантов seed не выполнять: `prisma/seed.ts` очищает учебный каталог и может уничтожить связанный прогресс. Также не использовать `prisma migrate reset`, `db push` или принудительные seed-команды как способ миграции production.

### Финальное переключение

1. Закончить занятия, остановить все записи на старом сайте, заморозить выпуск новых облачных версий. Снять финальную БД и файлы; записать время и контрольные суммы. Старое облако сохранить для отката.
2. Повторить проверенный перенос в новую БД, скопировать файлы, заменить подтверждённые URL. Настроить окружение и сборку. Следующая последовательность предполагает, что доработки раздела 6 уже выполнены:

```bash
npm run check-env
npm run lint
npm test
npx tsc --noEmit
npm run build
npm run start -- --hostname 127.0.0.1 --port 3100
```

3. Постоянный запуск оформить службой с рабочим каталогом, защищённым окружением, журналами и автоматическим перезапуском. Команда выше — проверочный запуск, не замена службе. При контейнеризации loopback/сеть настроить с учётом расположения прокси.
4. Провести приёмку, переключить DNS/адрес в согласованное окно. Старый `*.vercel.app` нельзя переназначить через DNS техникума: для него нужны перенаправление либо закрытие старого приложения. Проверить также технические production/preview URL, чтобы не осталось второй доступной для записи базы.
5. Проверить новый адрес из сети класса и, если требуется, из дома. Учитывать кэш DNS. Старый сайт до конца перехода не должен принимать записи в старую БД.
6. После согласованного периода наблюдения завершить отказ от облаков, удалить лишние копии по принятому порядку и отозвать больше не нужные доступы. Не удалять Supabase/Vercel сразу после первого успешного открытия страницы.

## 8. Приёмка и откат

Принимать перенос совместно с наставником:

- Сверены количества строк всех 23 прикладных таблиц и ключевые связи, сохранены ID, роли, хеши PIN и счётчики; проверены примеры XP, монет, достижений и истории работ. Для критичных полей сравнить значения/контрольные суммы, не ограничиваться количеством.
- Старый PIN ученика работает, вход наставника через `/mentor` работает; у ученика нет доступа к админским действиям. Проверены выход и повторный вход, редиректы на правильный HTTPS-домен.
- Курсы, уроки и ресурсы видны правильным группам; черновики скрыты. Прогресс сохраняется после обновления страницы, повторное прохождение не выдаёт награду повторно.
- Ручная работа отправляется, возвращается на доработку и принимается; видны старые версии и комментарии. Очное занятие и панель наставника обновляются.
- Все старые картинки открываются, новая загружается; изображения сохраняются после перезапуска/обновления сервиса. Сверены число и контрольные суммы файлов.
- Python/JS и встроенные материалы проверены с компьютера ученика в реальной сети. В браузере нет неожиданных запросов к отключённым облакам.
- `/api/health` возвращает HTTP 200 и `db: up`; при недоступной БД он должен давать 503. Отдельно проверены загрузки, TLS, автозапуск после перезагрузки, резервирование и основной сайт техникума.
- Интеграционные/E2E-тесты и `verify:restore` запускались только на выделенной тестовой БД. `verify:restore` создаёт и удаляет временные схемы; реальные данные требуют `--allow-personal-data`. Он сверяет количества строк, но не доказывает идентичность всех значений и не проверяет файлы Storage.

Откат до открытия записи на новом сайте: остановить новый сервис, вернуть старый адрес/маршрут, открыть записи в сохранённом старом окружении. После появления новых данных простой возврат потеряет их: сначала остановить запись, сохранить новую БД и файлы, согласовать перенос новых изменений или восстановление старого сервиса с актуальными данными. Две независимо записывающие версии одновременно не запускать.

## 9. Эксплуатация после переноса

Назначить ответственного за службу, TLS/DNS, обновления, дисковое место, логи, БД и восстановление. Настроить ежедневные копии БД и файлов с отдельной копией вне этого сервера; срок хранения и допустимую потерю данных согласовать. Ротация 60 JSON-файлов в текущем скрипте не означает, что расписание настроено, и не защищает от потери всего диска.

`npm run cleanup-attempts` удаляет попытки входа старше 24 часов и записи удалённых пользователей; при необходимости назначить ежедневное расписание с правильным окружением. В `vercel.json` crons нет. Периодически проверять восстановление на отдельной БД и доступность `/api/health`, файлов и основного сайта техникума.
